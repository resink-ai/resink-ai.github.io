# Sim Farm OKR — 2026-06-06

## Context

Engine 0.3 is the lift target this loop: we close retro P1 from 2026-05-23 by replacing engine 0.2.0's hard-coded `KEY_COLUMNS = ("user_id", "valid_from")` + payload `(email, country, valid_to, is_current)` with schema-driven join + payload columns read from a per-pair `--schema-ref` JSON file. The change unblocks resink-core's `dim_account` natural-column shape (`account_id` + `account_type` + `status`) — the isomorphic-column compromise NAMED in [resink-core's docs/architecture.md § Named deviations](../../../../repos/resink-ai/resink-core/docs/architecture.md) lifts when this lands. The two-loop forced-red-path carryover from 2026-05-16 / 2026-05-23 absorbs naturally as the final smoke against the live `make mvp-loop` driver under the new engine. Cross-team dependencies: **resink-core's orchestrator** writes per-dim `schema.json` next to each fixture/output parquet and passes `--schema-ref` (board O2 KR2.5); **DE is paused** this loop and coordinates schema-JSON shape via the request mechanism — if DE doesn't object by mid-loop the sim-farm-embedded spec stands, with optional migration to DE's `conventions/` tree next loop.

## Objectives

### O1: Ship engine 0.3 with schema-aware join + payload columns

- source: ceo-brief

Why it matters: This is retro P1 from loop 2026-05-11-1113 — the highest-priority architectural-debt item carried for two loops. Engine 0.2.0's shape-only multi-dim shipped semantically single-table (every dim must look like `dim_user` to satisfy hard-coded helpers); the multi-dim widening at 2026-05-23 forced resink-core into an isomorphic-column compromise for `dim_account` (synthetic `user_id`/`email`/`country` columns wrapping real `account_id`/`account_type`/`status`). Closing this lift (a) restores semantic correctness to resink-core's `dim_account` shape, (b) closes the third-loop carry, (c) unblocks any future third dim with a different PK name, (d) provides the first cross-team contract to receive the `Verified-against-environment` subsection per ADR-2026-05-16-003, and (e) absorbs the two-loop forced-red-path carryover into the new engine's end-to-end smoke. Backward compatibility is the additivity discipline carried from engine 0.2.0: omitting `--schema-ref` falls back to legacy hard-coded columns; legacy callers keep working.

## Risks

- **Schema-JSON spec coordination with DE — cross-team dependency under DE's paused posture.** Engine 0.3 cannot ship without an agreed schema-JSON shape, and DE is paused this loop with only a one-paragraph paused-team ack expected. Mitigation: sim-farm authors the spec embedded in its own contract update (KR1.4) and notifies DE via a one-line `teams/data-engineering/requests/<date>-dim-schema-json-shape.md` filing by mid-loop 2026-06-09. If DE doesn't object by 2026-06-09, the sim-farm-embedded spec stands; if DE objects, the spec migrates to DE's `conventions/dim-schema-json.md` next loop without breaking engine 0.3's contract (the in-memory format and `--schema-ref` arg shape stay the same; only the canonical owner moves).
- **Pair-position alignment of `--schema-ref` against `--fixture` is fragile under argparse `action="append"`.** If a user supplies `--schema-ref` for the second pair but not the first, the engine must align `--schema-ref` to the second pair-position, not the first. Mitigation: implement an explicit pair-builder that requires `--schema-ref` to be supplied positionally with a sentinel `--schema-ref=` (empty string) for "fall back to legacy for this pair"; the smoke test `test_schema_ref_omitted_falls_back_to_legacy_hardcoded` covers both the "all omitted" case and the explicit "this-pair-omitted" sentinel case.
- **Helper refactor accidentally regresses single-dim legacy path.** Pulling `KEY_COLUMNS` out of module scope into helper parameters could subtly break the existing 9 tests if any test references the module-level constant directly. Mitigation: the legacy constants stay defined at module scope as defaults; helpers accept them via parameter with the constants as default values; existing tests run unchanged. Diff-engine self-test (KR1.3's "13/13 green including all 9 existing tests") catches any regression on the first commit.
- **`make mvp-loop` regresses under the schema-aware shape if resink-core's per-dim schema.json doesn't land in the agreed shape.** If resink-core writes a different shape (e.g., nested `{"schema": {"key_columns": [...]}}` instead of flat `{"key_columns": [...]}`), engine 0.3 fails to parse. Mitigation: the schema-JSON shape is documented inline in the engine module docstring (KR1.2) and in the contract body update (KR1.4); resink-core opts in by matching the documented shape, or files a contract addendum naming a different shape — same negotiation pattern as 2026-05-23's `--pair` separator question. The minimum required keys (`key_columns`, `payload_columns`) are explicit; additional keys are ignored by engine 0.3 (additivity discipline).
- **Forced-red-path smoke (KR1.6) depends on a working `make mvp-loop` under the new schema-aware shape.** If the resink-core ↔ sim-farm coordination on schema.json paths slips past mid-loop, the red-path smoke can fall back to the **legacy single-dim hard-coded path** (engine invoked without `--schema-ref`, against last loop's `closed_loop_v0/` fixture) — the test of "does the Makefile propagate non-zero?" doesn't require schema-aware columns. The two-loop carryover closes regardless of resink-core's schema-aware delivery timing.
