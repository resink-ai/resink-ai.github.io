## Risks

- **C-ABI design surprise at smoke-test time** (brief Risk #1). Status code constants, FFI pointer-lifetime semantics, or the `NodeCtxC` struct shape could differ from ADR-2026-05-16-001 §1's recommended form once the actual implementation hits the smoke test. Mitigation per the brief: AE files an **in-loop ADR addendum** (or a sibling ADR) naming the actual signature that ships, rather than re-litigating the original ADR. The "verify-against-environment" discipline from ADR-2026-05-16-003 applies — AE confirms the actual built artifact's exported symbols (via `nm` or `objdump -T`) match the template's declared signature and the ABI crate's `extern "C"` declaration before declaring KR1.3 met. If a divergence is unavoidable, the addendum is itself a deliverable for this loop (small ADR; references the original; names the actual signature for resink-core's loop+1 consumption).
- **`libloading` toolchain or `cdylib` build failure on the IC's Mac.** The marketplace's reference workspace may not be configured to build a `cdylib`, or the Mac's Rust toolchain may need a `--target` flag for the right `.dylib` ABI. Mitigation: AE verifies `cargo build --release` succeeds for the codegen output as `cdylib` early in the loop (before authoring the smoke); if a Cargo.toml `crate-type = ["cdylib"]` edit is needed in the template's reference workspace, that edit is in-scope for KR1.1 (the template defines the build shape it expects). The fallback path is to ship the smoke with the `cargo build` invocation documented in DISPATCH.md (KR1.6 form (b)) and defer the in-test build automation to loop+1.
- **Built-artifact path discoverability for resink-core.** Resink-core's loop+1 work needs to find the `.so`/`.dylib` deterministically; if the path varies by toolchain version or platform, the scaffolded `plugin_loader.rs` integration becomes harder than the brief contemplated. Mitigation: KR1.6 explicitly requires a documented path; AE's preferred form (build script / Makefile target) handles the platform branch internally (`if Linux: .so; if Darwin: .dylib`). If the preferred form proves too large for this loop's scope, AE ships the README-snippet form (form (b)) and surfaces a one-line cross-team ask to resink-core's loop+1 brief recommending the build-script form be folded into the supervisor swap work.
- **Marketplace test regression from the template edit.** The 98/0/3 baseline could regress if existing snapshot tests pin the template's exact text and the C-ABI export changes the rendered output for existing fixtures. Mitigation: AE updates snapshot tests in the same commit as the template edit, with the diff noted in the exec summary so the regression-vs-update distinction is auditable. The test suite is owned by AE (per Bundle B's ritual edits); snapshot updates are in-scope.
- **AE bandwidth pull from non-O1 work.** Two specific temptations: (a) future codegen patterns from training spec §4.10 (`scd1_first_event`, `window_stats_with_decrement`, etc.) — the consolidation framing names these as out-of-scope until the dlopen plan closes; (b) any DISPATCH.md follow-up triggered by `claude` CLI's `--skill` flag (no this-loop signal that it's shipped). Mitigation: this loop's discipline is strict — AE EM gates discretionary pulls; any non-O1 work that isn't a same-day correctness fix to AE's existing skills is deferred with a one-line note for the 2026-06-13 brief. Brief O1's "Why it matters" framing makes this a single-deliverable loop; the discipline is informal but explicit in AE's own out-of-scope list below.
