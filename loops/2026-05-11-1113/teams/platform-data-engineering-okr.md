# Data Engineering OKR — 2026-05-23

## Context

Another light loop for DE — consolidation-flavored, not a new-surface loop. The [CEO brief](../../../../board/okrs/2026-05-11-1113-ceo-brief.md) widens the MVP fixture to two dims and three facts (O1) and lands the largest ADR batch the company has authored (O2, six ADRs). DE is named in four places: **O1 KR1.4** (ratify `xxHash64(seed=0)` byte-stably for resink-core's partition swap), **O1 KR1.6** (draft the `fact_account_open` schema fragment for the new fact stream targeting `dim_account`), **O6 KR6.2** (author a one-paragraph `pytz` DuckDB conventions doc), and **O2 KR2.4** (cooperate with the board's retroactive `type: rfc → type: contract` migration after ADR-2026-05-10-004 ratifies). None of these are new surfaces — they are the consolidation tail of the contract work that landed in loops 2026-05-10-2227-002 and 2026-05-16.

The two prior loops both carried the `type: rfc` workaround for hand-off contracts (Kafka ingress 2026-05-10; in-memory event source 2026-05-16); the brief retires that workaround this loop via ADR-2026-05-10-004 (board-owned). DE adds a third contract artifact (`fact_account_open` schema fragment) alongside, then participates in the migration. The pytz convention is the closure of the third consolidation item the 2026-05-16 retro surfaced from sim-farm's pyproject.

## Objectives

### O1: Close DE's consolidation tail — fact_account_open schema, xxHash64 ratification, pytz conventions doc, and contract-type migration cooperation

- source: ceo-brief
- links.source: [board/okrs/2026-05-11-1113-ceo-brief.md](../../../../board/okrs/2026-05-11-1113-ceo-brief.md) — O1 KR1.4, O1 KR1.6, O6 KR6.2, O2 KR2.4

Why it matters: Resink-core's O1 widening introduces `dim_account_scd2` and a new fact stream `fact_account_open`. DE owns event-source contracts; the new fact stream needs a named schema fragment that downstream code (orchestrator's `generate.py`, supervisor's in-memory event source, sim-farm's diff engine, codegen's `schema_json` payload) can read first rather than inferring from the parquet. The xxHash64 ratification gives resink-core a byte-stable citation for the partition swap (CEO brief O1 KR1.4 is the code; the ratification entry is the spec hook). The pytz conventions doc closes a hygiene item the 2026-05-16 retro raised about sim-farm's pyproject (the dep is shipped; DE just records the convention). The contract-type migration cooperation closes three loops of `type: rfc` filings under the workaround now that ADR-2026-05-10-004 lands this loop.

**Key results**

- KR1.1: **fact_account_open schema fragment lands** as an additive section to the existing [Kafka ingress contract](../contracts/2026-05-10-kafka-ingress.md) (§9, new section) and as a parallel cross-link from the [in-memory event-source contract](../contracts/2026-05-16-in-memory-event-source.md) — **not a new contract file** (chosen path: addendum to both existing contracts, not a third standalone file). The fragment names: (a) primary-key field `account_id` (single PK, per Kafka contract §2's "exactly one primary-key field per ingress topic"); (b) op kinds emitted by the fixture (`insert` only — accounts open, they don't update or delete in the v1 fixture); (c) the SCD2-shaped `after` row schema matching `dim_account_fixture`'s columns `(account_id, user_id, account_type, status, valid_from, valid_to, is_current)` as defined by resink-core's O1 KR1.1; (d) cross-dim referential note that `account.user_id` references `dim_user.user_id` (the diff seam — DE does not own the join, but names the reference so the contract is self-documenting); (e) topic naming under Kafka contract §1: `nanofab.ingress.<tenant>.fact_account_open` and partitioning by `xxHash64(account_id)` per Kafka contract §2. Maps to CEO brief O1 KR1.6.

- KR1.2: **xxHash64(seed=0) ratification entry** lands as a new normative subsection inside Kafka contract §2 (or as a §2.1 sibling — DE picks during build) tagged `Ratification (2026-05-23)` so resink-core's `partition()` impl can cite it byte-stably. Entry includes: (a) a worked example with one concrete key (`account_id=42` as a string; `key_bytes = b"42"`; expected `xxh64(b"42", 0) = <hex value>`); (b) explicit statement that the canonical UTF-8 byte encoding is the **decimal string form of the integer PK** for the MVP fixture (matching `derive_facts.py`'s key derivation), not the binary `i64` encoding — pinned so producer/consumer agree byte-for-byte; (c) explicit statement that `shard_count=4` for the multi-shard widened fixture (CEO brief O1 KR1.4) and `shard_count=1` for the single-shard MVP path stays valid (in-memory contract §4); (d) the `twox-hash::xxh64::xxh64` Rust function as the reference impl point (matching what resink-core uses in the supervisor swap). The in-memory contract's §4 gains a one-line back-reference to the ratification entry, mirroring the existing 2026-05-16 back-reference pattern. Maps to CEO brief O1 KR1.4.

- KR1.3: **`pytz` DuckDB conventions doc lands** as a new file at `teams/platform/data-engineering/conventions/duckdb.md` (chosen path — new `conventions/` directory at the team root, matching the brief's explicit pointer to `teams/platform/data-engineering/conventions/duckdb.md`). One-paragraph normative entry stating that DuckDB's Python driver requires `pytz` at runtime to materialize `TIMESTAMPTZ` rows, and that consumers depending on DuckDB-via-Python (notably sim-farm's diff engine) **must declare `pytz` as a hard dep** in their `pyproject.toml`. Links the canonical example: [`repos/resink-ai/resink-core/sim-farm/pyproject.toml`](../../../../repos/resink-ai/resink-core/sim-farm/pyproject.toml). Frontmatter follows the team's convention pattern (`type: rfc` filed as the workaround if landed before ADR-004 ratifies, then migrated to `type: contract` in the same loop per O2 KR2.4; or `type: contract` directly if the build-phase ordering puts ADR-004 first). `status: active` on land. Maps to CEO brief O6 KR6.2.

- KR1.4: **Contract-type migration cooperation.** When the board ratifies ADR-2026-05-10-004 (CEO brief O2 KR2.1) and orchestrates the retroactive `type: rfc → type: contract` migration (CEO brief O2 KR2.4), DE confirms the migration on its three contract files: [`2026-05-10-kafka-ingress.md`](../contracts/2026-05-10-kafka-ingress.md), [`2026-05-16-in-memory-event-source.md`](../contracts/2026-05-16-in-memory-event-source.md), and (if KR1.3 lands the conventions doc as `type: rfc` first) `conventions/duckdb.md`. Confirmation = read the board's migration commit, sanity-check that the type-note HTML comments at the top of each contract (the ones citing "conventions.md does not include `contract` in the type enum") are also removed or revised to point at ADR-004, and ack to the board. If the board offers DE the option to author the migration directly, DE accepts; if the board orchestrates centrally, DE just confirms. No body edits to the contracts beyond frontmatter `type` and the type-note removal. Maps to CEO brief O2 KR2.4.

## Risks

- **`fact_account_open` schema diverges from resink-core's actual `dim_account_fixture` shape.** Mitigation: the brief names the exact column set verbatim (CEO brief O1 KR1.1); DE drafts against that set and reconciles same-day if resink-core's emitted `schema.json` diverges. The schema fragment is additive and live; any divergence resolves by a one-day addendum, not a contract revision.
- **ADR-004 ratification slips within the loop.** Mitigation: KR1.3 lands the conventions doc filable as `type: rfc` under the existing workaround (consistent with how the two prior contract loops shipped) and migrates same-loop once ADR-004 lands; KR1.4 cooperation is a confirmation step, not a blocker. If ADR-004 itself slips past the loop, DE's contract files stay as `type: rfc` for one more loop — defensible per the existing workaround comment.
- **xxHash64 ratification entry pins a byte value that diverges from resink-core's runtime observation.** Mitigation: the worked example is a small computation; if resink-core's `twox-hash` crate version produces a different value, DE corrects the entry the same day. The hash function + seed + input encoding are pinned (and already pinned across two prior contracts); only the worked-example hex value is at risk.
- **`type: rfc → type: contract` migration touches three contract files plus possibly the conventions doc; coordination with the board's central orchestration could collide on file edits.** Mitigation: the board owns the migration per CEO brief O2 KR2.4; DE waits for the board's signal before touching frontmatter and confirms after. If the board offers DE the direct-authorship option, DE accepts and the migration is one commit per file.
