1. What Resink.ai does

Data teams everywhere face the same problem: fact events arrive constantly (sign-ups, profile updates, account opens, trades) and need to be projected into dimension tables (a current snapshot of who each user is, what each account holds, etc.) with full history preserved. The classical solution is hand-authored SCD2 (slowly-changing-dimension type 2) maintainer code per dim, hand-tuned per tenant, hand-deployed per cluster — weeks of engineering per new dim table.

Resink.ai compresses that to minutes. The flow:

  1. A customer hands us a sample of fact parquets (or describes the dim shape).
  2. An LLM-driven orchestrator proposes the dim-table design, asks clarifying questions when there are trade-offs, and on confirmation generates the per-dim Rust maintainer code deterministically from a hand-authored template + the schema.
  3. The generated crates compile (verified by cargo build + cargo test); a multi-tenant Rust supervisor loads them, routes the fact streams through per-key shards, and emits the SCD2 dim-table output.
  4. A diff engine byte-compares the output against the customer’s fixture and emits a single verdict.json: pass or fail, with per-key mismatch records on fail.
  5. The validated pipeline ships to a real Kubernetes cluster via a per-tenant Helm chart.

The differentiation isn’t “use AI to write code”; it’s AI-generated code under a deterministic, verifiable, multi-tenant runtime. The generated Rust is byte-identical for identical inputs, the runtime is Rust (no JVM, no GC stalls), and every claim about the pipeline is backed by an on-disk verdict file the operator can audit.

2. What’s running today (with evidence)

Each bullet is a present-tense capability backed by an on-disk verdict, a test exit code, or a checked-in artifact. Every file path resolves in our public-mirror gitbook at blog.resink.ai.

  • The full closed loop is GREEN. make mvp-loop runs the entire training pipeline against a synthetic tenant fixture and exits 0 with verdict=pass mismatches=0. Two dim-tables (dim_user, dim_account) processed through one supervisor binary; three fact streams (fact_sign_up, fact_profile_update, fact_account_open); 4 logical shards per dim; byte-stable hashing. verified
  • LLM-generated Rust compiles deterministically. The orchestrator dispatches our nanofab:codegen-scd2-node Claude Code skill, which slot-fills a hand-authored Rust template against the schema. Given identical (schema, pattern_name) inputs, the skill produces byte-identical Rust source (the content-hash dedup property the runtime relies on). First end-to-end LLM-driven attempt (loop 2026-05-16) produced compilable Rust with zero template iterations — ~$0.77 in API cost, ~106s wall-clock on a developer laptop. verified
  • The supervisor runs on a real Kubernetes cluster. The Helm chart has been helm install-ed on our home cluster (4 nodes, k8s v1.33.11) at loop 2026-05-12-0645. Pods schedule, exercise the canonical happy path, and uninstall cleanly. Two latent chart bugs surfaced + were fixed in flight; both became failure-mode entries in our SRE deployment runbook. verified
  • Hot-swap correctness verified at the supervisor level. Our long-running ABI restoration plan (ADR-2026-05-16-001) closed on 2026-05-13: the supervisor can load plugin library v1, process events, unload, load v2, and continue — verified by a supervisor-integrated test that exercises the production plugin_loader::PluginNode code path against two AE-template-derived cdylibs with a documented one-line behavioral deviation between them. Five-loop, three-step engineering arc complete. verified
  • Operator-readable cluster observability shipped. A new observability Claude Code plugin emits a self-contained HTML snapshot of the cluster’s state on demand (node table, per-namespace pod table with status colorising, recent warning events). The first run (2026-05-13) is committed at board/reports/2026-05-13-cluster-snapshot.html — 4 nodes ready, 21 pods running, zero warning events. verified
  • A power-user CLI ships. The resink binary (5 read-only subcommands: workspace status, verdict latest, manifest get, table head, trace tail) gives a developer first-class access to the tenant workspace produced by make mvp-loop. Sized for v1; written in Rust; ~6 unit tests passing. verified
  • Marketplace of 4 cross-platform plugins. Our internal plugin marketplace at resink-ai/resink-marketplace ships per-platform manifests (Claude Code, Codex CLI, Gemini CLI, OpenCode) for: agent-forge (the skill-authoring toolkit), org-os (the rituals our internal operations run on), nanofab (the codegen skill), observability (cluster snapshots). 89 manifest-shape tests passing. verified
  • First CI gate on a private-by-default infrastructure repo. The resink-core remote now runs a GitHub Actions helm-lint + helm-template gate on every PR + push-to-master. 3. Architecture in one diagram

The closed loop is a seven-step pipeline. Each arrow is labelled with the data artifact crossing the boundary.

+-----------------------+
|     fixture           |   (synthetic tenant or customer-provided)
|   schema + facts      |
+-----------------------+
           |
           |  schema.json + fact_*.parquet
           v
+-----------------------+
|    orchestrator       |   (Python; dispatches AE's claude skill)
|  AE codegen skill x N |   nanofab:codegen-scd2-node
+-----------------------+
           |
           |  per-dim Cargo crate (lib.rs + Cargo.toml + STATUS.json)
           v
+-----------------------+
|     cargo build       |   (per-node crate, then supervisor host)
|   per-dim node x N    |
+-----------------------+
           |
           |  manifest.yaml + .nanofab/release_seal.json
           v
+-----------------------+
|     coordinator       |   (nanofab-coordinator binary)
|   validates seal      |
+-----------------------+
           |
           |  validated release_seal + DAG ready signal
           v
+-----------------------+
|     supervisor        |   (nanofab-supervisor binary)
|  multi-node, sharded  |   xxHash64(key, seed=0) % shard_count
+-----------------------+
           |
           |  dim_*_output.parquet + trace.jsonl
           v
+-----------------------+
|    diff engine        |   (sim-farm, Mode-A, engine_version 0.2.0)
|  byte-compare output  |
+-----------------------+
           |
           |  verdict.json (pass | fail + mismatch records)
           v
+-----------------------+
|       deploy          |   (helm chart -> real k8s cluster)
|   per-tenant chart    |
+-----------------------+

The pipeline runs end-to-end on a developer laptop (make mvp-loop) without any cloud credentials or LLM API key in the default path. CLAUDE_DISPATCH=1 opts in to LLM-driven dispatch for the codegen step; the default uses in-process deterministic slot-fill so the loop is reproducible offline.

5. Closed engineering arcs

Two multi-loop engineering arcs closed cleanly. Each demonstrates that named technical debt + a time-boxed restoration plan works in practice.

ADR-2026-05-16-001: dlopen restoration (five loops, three steps)

The MVP supervisor took a deliberate deviation from the runtime spec: it linked per-tenant node crates as Cargo path-deps rather than loading them via dlopen. The trade-off: simpler v1, no hot-swap capability. The ADR named the deviation, time-boxed the restoration to three engineering loops, and committed to closure.

Closed at loop 2026-05-13-1022. Step 1 (AE template extension to add the nanofab_node_process C-ABI symbol) landed 2026-06-06. Step 2 (supervisor swap to libloading::Library with a feature-gated static-linking fallback) landed 2026-05-11-2153. Step 3 (hot-swap correctness test against two distinct plugin libraries) landed 2026-05-13-1022 with one mid-arc planning re-shape (the third-consecutive slip resolved via a split into AE-only + resink-core-only sub-deliverables). The runtime spec’s hot-swap property is now verified at the supervisor’s production load path.

ADR-2026-05-09-001: bottom-up flow (17 tasks, three bundles)

Our internal operations process (the “org-os”) was scaffolded over three loops as 17 named tasks: Bundle A (rituals foundation, 5 tasks, 2026-05-10); Bundle B (executive loop + team-intake + retro shapes, 7 tasks, 2026-05-23); Bundle C (roles + walks + README, 5 tasks, 2026-05-30). Full discharge of the original plan. The org-os process is now self-describing — the docs that explain how we operate are themselves authored under the process they describe.

6. Honest deferrals

What the system does not yet do, named explicitly so the boundary is clear.

  • Real Kafka / event-stream ingestion. The supervisor reads parquet event-source files; the Kafka contract is specified but the consumer code does not ship.
  • Persistent state backend. SCD2 state is held in-process per supervisor instance; the path to a real KV (Redis / DynamoDB / similar) is named but not implemented.
  • Multi-tenant supervisor sharing. One supervisor process per tenant today; cross-tenant supervisor sharing is on the roadmap, not the codebase.
  • Cross-swap state observability. The hot-swap test (closed above) verifies the load + unload + reload cycle through the production code path. The full DEVIATION.md contract specifies a richer read-back (assert that v2’s row-close behavior is observably active after the swap) which requires a supervisor-side NodeCtx bridge — named as step 3.5 follow-up to the closed ADR. Demand-driven; no specific loop scheduled.
  • Sim-farm Modes B and C. Mode A (file-vs-file diff) is shipped; Mode B (streaming Rust differ) and Mode C (sidecar comparison) are spec’d but not implemented.
  • Customer-facing UI. The system is exercised via CLI + Makefile + a power-user binary. A web UI is not in tree.
  • Branch protection / required-CI on the private engineering remote. Helm CI runs on every PR; making the helm gate a required check requires a paid GitHub plan (free plan blocks branch protection on private repos). Tracked as a contributor-count-driven decision.
  • Cargo CI cross-repo step. The supervisor’s codegen path-deps depend on the marketplace repo as a sibling; CI clone needs a deploy key, scoped PAT, or in-repo test fixtures. Three private-compatible options documented; no public-repo conversion required.
Note on honesty. Every deferral above corresponds to a named follow-up in our internal artifacts (ADRs, retros, exec summaries). We surface them here because hidden deferrals turn into hidden surprises; the engineering trade-offs are clearer when they’re visible.
